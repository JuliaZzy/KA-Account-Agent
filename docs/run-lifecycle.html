一次聊天 run：函数、队列与数据库

execute_run() 只处理一个 run 的一次投递；父 run 等子 run 时会释放租约，子任务完成后再重新入队。

1 · HTTP 收到消息

session_router.message()
→ service.handle_message()
读取：sessions
内存：请求体、附件

2 · 创建 queued run

enqueue_chat_run()
→ create_agent_run()
→ dispatch_pending()
同一 PG 事务：agent_runs、run_events(run.created)、outbox_jobs
随后：dispatch_pending() 扫 pending outbox，execute_run.delay(run_id)，再标记 outbox 已派发（与 broker 分两段事务，可重扫）
注意：此时还没有 agent_steps

3 · Celery 领一次任务

celery.tasks.execute_run()
→ run_worker.work_once()
→ claim_chat_turn()
更新：agent_runs(lease/status)
写入：run_events(run.started)

4 · 父 run 做 PLAN

execute_chat()
→ execute_parent()
→ make_plan()
写入：agent_steps、model_calls、usage_records
产物：tasks[] 计划

5 · 按波派子 run

dispatch_wave()
→ begin_turn()（Redis）
→ commit_task_wave()
→ dispatch_pending()
顺序：先 Redis 计数与信箱，再同一 PG 事务写子 agent_runs、run.created、outbox_jobs、父 tool.started、父 checkpoint、父 waiting_for_tasks；commit 后对子 outbox 调 dispatch_pending() 发 Celery
不可同事务：Redis、broker 消息

6 · 子 run 执行任务

execute_run()
→ work_once() / claim_chat_turn()
→ execute_task() → tool.fn(...)
写入（PG）：子 run_events(run.started)、agent_steps、tool_calls、model_calls、output_json
结尾 finish_child 前：账本只在 PG；崩溃靠子 run 重试与子 output_json 幂等恢复

7 · 波次完成，唤醒父 run

finish_child()
→ record_child_wave_result()
→ store_result()（Redis）
→ requeue_waiting_tasks() → dispatch_pending()
同一 PG 事务：父 checkpoint.results + 父 tool.completed/failed
随后：Redis 递减 left；left=0 时另一 PG 事务父 → queued + outbox + run.resumed，再 dispatch_pending()
慢路径：Redis 丢则 sweep_waiting_for_tasks（默认 15 分钟）补唤醒

8 · ANSWER 并完成

execute_parent()
→ compose_answer()
→ save_reply()
→ _finish_claimed() / complete_run()
写入：model_calls、usage_records、sessions.history
终态：agent_runs → succeeded
5–7 会按依赖重复；没有 tasks 时，4 直接进入 8。首次无标题会话还会并行创建一个 OPEN run，执行 execute_open() 写 sessions.title / tags。

控制流文字版：鉴权、幂等、重试、确认和清扫

正常路径在上面；这里补充“为什么会停下、什么时候会再投、什么情况下会失败”。每张卡都标出实际函数和文件。

1 · Run API 鉴权和入口闸门

backend/routes/runs.py · get_current_user()
backend/services/entry_guard.py · admit_create() / admit_read()

Run API：X-User-Id → db.user() → distributor_id(org_id)，请求里的 org 不参与授权。随后用 Redis 固定窗口限流和并发闸门；失败在 HTTP 层返回 401 UNAUTHENTICATED 或 429 RATE_LIMITED。聊天 message 路由另外检查 session，再由 enqueue 使用 session 的 user/partnership。

2 · 幂等地创建 run

run_service.create_run() / chat_run.enqueue_chat_run()
find_run_by_idempotency_key() → create_agent_run()

同一事务写入：agent_runs、run.created、outbox_jobs。同一个幂等键直接返回已有 run。创建时还没有 agent_steps；模型或工具真正开始后才写 step。

3 · outbox 投递和 worker 领取

dispatcher.dispatch_pending()
celery.tasks.execute_run() → run_worker.work_once()
entry_guard.acquire_run() → claim_chat_turn()

Redis：DB 0 放锁和闸门，DB 1 是 Celery broker，DB 2 放 wave 结果。数据库标记 dispatched 和发送 broker 消息是两个事务，所以 sweeper 会补投。SessionBusy 约 2 秒后重试，队列关闭约 30 秒后重试。

4 · PLAN、子 run 和 waiting 状态

chat_run.execute_chat() → parent.execute_parent()
plan.make_plan() → gather.dispatch_wave()
gather._enqueue_child() / mark_waiting_for_tasks()

父 run 派出一波子 run 后进入 waiting_for_tasks，释放租约；每个 child 通过自己的 execute_run() 执行。结果写入 Postgres checkpoint，再用 Redis DB 2 做快速计数和唤醒。

5 · 模型和上游错误怎么重试

llm.calls.call_model()
ProviderError / ModelCapacityExceeded
run_worker._finish_claimed() → schedule_retry()

厂商 429、5xx、超时、断网：读取 Retry-After 或使用 jitter 退避，释放模型和 run 租约，并以 spend_attempt=False 重新排队。401/403、400/422、坏响应和预算超限不重试。熔断器按 provider 连续失败后暂时停止请求。

6 · 工具先校验，再决定是否执行

run_loop._prepare_tool() / _finish_tool()
claim_tool_call() / complete_tool_call()

依次检查工具是否存在、开关、参数 schema、用户权限、调用预算和业务幂等键。读工具错误最多重试 2 次；发信和 MCP 等副作用默认不自动重试。重复业务键记 skipped_duplicate；外部系统已收到但结果丢失记 response_lost 并要求人工复核。

7 · Run 级业务重试和死信

run_worker._settle()
db/database/queue.py · schedule_retry()

普通异常、模型解析失败等尚未形成可用业务结果的错误，按 1 分钟、5 分钟、15 分钟重试，最多 3 次。耗尽后 agent_runs → failed，并写入 dead_letter_jobs。基础设施重试不增加业务次数，主要由最大运行时长兜底。

8 · 确认、跳过和取消

db.mark_waiting_for_user()
routes/runs.py · resume_run() / cancel_run()
run_service.resume_run() / cancel_run() → request_run_cancel()

需要人工决定的工具先停在 waiting_for_user。确认或跳过后重新变成 queued 并投递；skip 不调用工具。取消接口只先写 cancel_requested_at，worker 收到后才转为 cancelled。关页面或断开 SSE 不会取消 run。

9 · sweeper 每 15 秒补救一次

services/sweeper.py · sweep()
sweep_expired_leases() / sweep_waiting_for_tasks()
sweep_attention() / republish_unclaimed() / dispatch_pending()

它不调模型、不执行工具。租约过期则取消、重新排队或失败；waiting_for_tasks 超过 15 分钟且子任务都终态时重新排队；排队过久只记 stale；waiting_for_user 超过一天只提醒，不替用户确认；悬挂副作用转成 response_lost。

10 · 事件流、实时正文和追踪

routes/runs.py · events() / stream_run_events()
services/run_stream.py · iter_event_stream()
db.note_running_reply() → run.reply_updated

run_events 是按 sequence 保存的事实，Postgres NOTIFY 只负责唤醒 SSE。生成中的正文在 output_json.text；generation_id 变化时前端丢掉失败尝试的半截文本。终态后页面再读取 sessions.history。

状态速查：queued → running → waiting_for_tasks → queued → succeeded；需要人时 running → waiting_for_user → queued；取消可从 queued / waiting_for_user / waiting_for_tasks 进入 cancelled；业务重试耗尽进入 failed；重跑会新建 run，parent_run_id 指向旧 run，owner_run_id 表示本轮父子调度关系。

# 实验：冒烟 S4 — 首批冷启动，单用户 vs 多用户（各 30 条，worker 冷启动）

- **第几次**：冒烟 S4（相对 [`S1 r2`](02-s1-r2-smoke-concurrency-5.md) 和 [`S2`](03-s2-multiuser-20.md)：S1 第一波 11–12s、S2 第一波 6–7s，这一轮专门查原因）
- **日期**：2026-11-09（UTC 2026-11-10T03:23Z–03:26Z）
- **代码**：与 A2 相同，未改代码
- **原始文件**：[`exports/load-test-smoke-s4-r1-single-30.json`](../exports/load-test-smoke-s4-r1-single-30.json)、[`exports/load-test-smoke-s4-r2-multi-30.json`](../exports/load-test-smoke-s4-r2-multi-30.json)、[`exports/load-test-smoke-s4-r3-single-30.json`](../exports/load-test-smoke-s4-r3-single-30.json)（同名 `.log`）

S2 的记录保持原样不改；S2 当时的解释（多用户让 P95 降低、尾部是 soft-busy）与本轮结果不一致，以本记录为准。

## 目的

验证两个假设：

1. **用户数**：单用户的第一波比多用户慢，是因为用户闸门 / soft-busy（S2 当时的解释）。
2. **前缀缓存**：第一波慢是因为缓存没命中。

另外把「首批冷启动」本身量出来。

## 设计

要可比，保持不变的是**总条数和并发**，只改用户数。S1(10 条单用户) 对 S2(30 条三用户) 会把「用户数」和「样本量 / 波数」混在一起，所以没有那样做。

| 轮次 | 用户 | 条数 | 并发 | 每轮前 |
|---|---|---|---|---|
| r1 | 单用户（chen） | 30 | 5 | 重启 worker 和 title-worker |
| r2 | 三用户（chen / lin / zhou，各 10） | 30 | 5 | 同上 |
| r3 | 单用户（chen） | 30 | 5 | 同上 |

r3 重复 r1，用来看单用户内部的重复性；缓存温度没有强行控制，而是逐次调用记录命中 token，事后归因。模板、timeout、`GATE_USER=5` 与前面相同。

## 结果

| 指标 | r1 单用户 | r2 三用户 | r3 单用户 |
|---|---|---|---|
| 请求 / 成功 / 超时 | 30 / 30 / 0 | 30 / 30 / 0 | 30 / 30 / 0 |
| 成功 P50 | 4.69s | 4.64s | 4.58s |
| 成功 P95 | 8.46s | 8.46s | 8.22s |
| 成功 max | 8.62s | 8.88s | 9.28s |
| **第一波 5 条** | 8.0–8.6s | 8.0–8.9s | 7.8–9.3s |
| 其余 25 条中位数 | 4.62s | 4.52s | 4.56s |
| 每请求花费 | ¥0.000307 | ¥0.000265 | ¥0.000261 |

三轮几乎一样。第一波约 8s，之后稳定约 4.5s；单用户和三用户没有差别。

### 第一波多出来的 ~3.5s 花在哪

用 `agent_runs` 时间戳拆开（`chat` Run）：

| | 排队（`started_at − created_at`） | 执行（`ended_at − started_at`） |
|---|---|---|
| 第一波（5 条） | 约 1.1–1.4s | 约 6.3–7.8s |
| 其余 25 条（中位数） | 约 0.03s | 约 4.3s |

再看账本里每次模型调用自己的耗时（`model_calls.latency_ms`）：首批 10 次 chat 调用的中位数 2.0–2.2s，与其余 50 次（2.05–2.11s）相同，三轮都是。

一条 chat 请求有两次模型调用（PLAN + ANSWER，各约 2.1s，共约 4.2s）。所以第一波多出来的时间**不在模型调用里**，而在模型调用之外：

- 约 1.2s 的排队：worker 进程刚重启，子进程首次领任务；
- 约 2.5s 的执行内开销：模型调用之外的首次初始化（具体是哪一段，本实验没有拆，不做断言）。

### 前缀缓存的作用

| | r1 | r2 | r3 |
|---|---|---|---|
| 前 10 次 chat 调用缓存命中率 | **15.9%**（冷） | 79.6% | 79.6% |
| 其余 50 次 chat 调用命中率 | 79.6% | 79.6% | 79.6% |
| 第一波耗时 | 8.0–8.6s | 8.0–8.9s | 7.8–9.3s |
| chat 模型调用延迟中位数（命中 ≥50% / <50%） | 2.20s / 2.10s | 2.08s / 2.04s | 2.01s / 2.13s |

r1 起步时缓存是冷的（距离上一轮实验约 30 分钟），r2/r3 起步时是热的，但第一波耗时没有区别，命中与否的单次调用延迟也没有区别。**缓存影响的是花费，不是延迟。** r1 因为开头缓存冷，每请求多花约 ¥0.00004（¥0.000307 对 ¥0.000263 左右，约 +15%）。

## 结论

1. **假设 1 不成立**：同样冷启动、同样总条数，单用户和三用户的 P50、P95、第一波耗时一致。多用户并没有让第一波变快。S2 里「多用户后 P95 降低」更可能来自样本量不同（S1 10 条、S2 20 条）、第一波冷启动程度不同，以及当时 Qwen async bug 带来的 fallback 差异，而不是用户数；S1 / S2 当时没有这些对照数据，所以这只是与本轮结果一致的解释，不是对旧数据的重新测量。
2. **假设 2 不成立（对延迟）**：前缀缓存冷热不改变单次模型调用延迟，也不改变第一波耗时；它只影响花费，冷缓存约多 15%。
3. **首批冷启动是真实存在的**：worker 重启后第一波 5 条约 +3.5s（排队约 1.2s + 执行内开销约 2.5s），之后稳定。这个开销不依赖用户数、缓存和模型。
4. **对基线的含义**：A1 r2 / A2 的 P95 里包含第一波冷启动。A2 之所以没有 >10s 的尾巴，是因为 worker 在 A1 r2 之后一直是热的。正式基线应在报告里注明「worker 已预热」，或在压测前加几条预热请求。
5. **可选优化（本轮不做）**：worker 启动时预热（预导入模块、建立 DB / Redis / HTTP 连接池），可消除这 ~3.5s。只影响部署或重启后的头几个请求，优先级低。
6. 下一步：A3（2000 条）。压测前 worker 保持热状态，与 A1 r2 / A2 条件一致。

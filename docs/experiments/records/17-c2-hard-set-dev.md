# 实验 C2：困难题开发集上的 workflow 与 ReAct 对照

- **题集**：`golden_hard_v1.jsonl`（`build_golden_hard.py` 由 `golden_hard_v1.template.jsonl` 和 seed_v1 CSV 生成，数字全部由数据算出，生成时有断言）。
- **划分**：序号奇数为开发集，偶数为留出集。**本记录只跑了开发集**（`t2s-13/15/17/19/21/23/25/27/29`、`rpt-09`，每条 3 次，并发 1）；留出集还没跑，只在调完之后跑一次。
- **两个系统**：同 [16-c](16-c-text2sql-workflow-vs-react.md)，`KA_TEXT2SQL_IMPL=legacy|react`；报表路径的取数也已走同一开关。

## 对题集做的修改（模板里的假设与种子不符）

| 题 | 问题 | 处理 |
|---|---|---|

| `t2s-27` | 一个品牌只有 8 个产品，"列出所有产品"不会超过提示的 50 行 | 改为列出所有采购单明细行（99 行，超过 50 行，未到 100 行的系统上限） |

**系统触顶（LIMIT 100/200）在这份种子里无法触发**：任何一个合作关系的明细行最多 99 行。所以"结果太大要重写"这条路径用这批题测不到，只能测"提示里只放 50 行"这一半。

## 观察

1. **ReAct 的优势集中在"第一次写错，看到结果再改"的两类题**：`t2s-19`（类型错误）和 `t2s-23`（空结果后放宽名称）。旧方案在 `t2s-19` 里对同一个 `ROUND` 报错重写了三次都没修好，`t2s-23` 第一次查空之后直接答"没有数据"（旧方案只有失败才重写，空结果不触发）。ReAct 在这两题 6/6 通过。这是上一轮 36 题里看不到的。
2. **`t2s-15` 两边都有问题**：旧方案 3 次都答"结果被截断（仅显示前 5 条）"，ReAct 有 1 次自己数错（答 6 张、50%，实际 5 张、41.7%）。
3. **`t2s-27` 的 1 次失败不是 text2sql 的问题（更正）**：规划模型把"所有采购单"改写成"所有**未完成**采购单"再交给查数，ReAct 只是照问题执行（`status <> 'completed'`，9 行）。原始 trace 里规划输出的 `question` 字段已经带了"未完成"。上一版把它记成"ReAct 自己加了筛选"，是错的。
4. **成本只贵约 16%**（¥0.0057 对 ¥0.0049），比上轮（约 2.5 倍）小得多：旧方案失败时反复重写和反思，也在花钱。P95 差距更明显（15.5s 对 37.8s）。
5. **`rpt-09` 两边都 0/3，且不是 text2sql 的结构问题**：报表路径自己拆问题取数，没有走规划的 `required_columns`，回答里还出现"9 月无确认采购"之类与数据不符的说法。`handoff_columns` 的判分也只认 `quantity` 这个字面列名，没有别名表（`line_total` 有）。`rpt-08/09` 先不计入这次结构对照。

## 为什么只有 3 道题能区分结构

看两边第一条 SQL（`golden-hard-dev-*.jsonl` 的 `executed_sql`）：

| 题 | 两边的做法 | 为什么没区分度 |
|---|---|---|
| `t2s-13`、`t2s-17`、`t2s-29` | 都用 `TO_CHAR(submitted_at,'YYYY-MM')`、`DATE_TRUNC`、`ROUND(CAST(... AS DECIMAL),2)` | 题集的类型陷阱是按 sqlite 的 CSV 想的；线上库里 `submitted_at` 是 `timestamptz`，列注释写明了，模型直接用 `TO_CHAR` / `DATE_TRUNC`，不会撞"文本日期"；`ROUND` 它们也习惯先转型 |
| `t2s-21` | 都按 SKU 精确过滤 | 题本身是对照 |
| `t2s-25` | 都查了 `distributor_id AS user_id`（解释错了"用户"），但回答"没有订单"，硬检查只看有没有说没有数据 | **两边其实都做错了**，只是判分看不出来，是评测的盲点 |
| `t2s-27` | 两边 SQL 相同，`LIMIT 100` 大于 99 行 | 没触顶，差别只在规划阶段的改写 |
| `t2s-15`、`t2s-19`、`t2s-23` | 第一条 SQL 报错、返回空，或返回的是明细而不是结果 | **只有这三道的"第一次就对"概率低**，后面怎么处理才拉开差距 |

结论：只有当第一次的 SQL 会错或会空时，循环与固定流水线才不同。凡是模型一次写对的题（也包括 `t2s-25` 这种"错了但判分看不出来"的），两边没有区别。

## `t2s-15`、`t2s-27` 到底在哪里失败

- **`t2s-15` ReAct 第 1 次**：SQL 是对的（返回 12 张订单的金额和 `above_avg` 布尔值），**回答阶段的模型自己数了行**，数成 6 张（实际 5 张）。即：把"占比"这种最终指标留给 LLM 去数，是 SQL 层该做的。
  - ReAct 提示只写了"求总数、总额时在 SQL 中聚合"，没有覆盖"计数、占比"；旧方案的 SQL 提示有"计数、求和或总额时返回聚合结果，不要把明细列出来让读者自己加总"，**两边的规则不对等**（这是上一轮对齐时遗漏的）。
  - 旧方案 3 次：SQL 只返回了高于平均的 5 张单，没有分母，回答模型又把结果说成"被截断（仅显示前 5 条）"，是 SQL 不完整加回答误读，不是真的截断。
- **`t2s-27` ReAct 第 1 次**：规划阶段把问题改写成"所有未完成采购单"，text2sql 只是照做。**这是规划提示的问题，不是 text2sql 的**。

## 报表路径（`backend/report/turn.py`）与 `rpt-08/09`

报表路径是一条独立的流水线，不走编排规划的 `columns` / `deliver`：

1. 固定六节大纲（关键指标、摘要、业绩表现、库存情况、下一周期计划、问题与风险），由 `REPORT_QUESTIONS_PROMPT` 的独立规划调用把用户这句话拆成每节至多 3 个问题。
2. `_query` 逐个问题调用 `answer_question`（现在走 `KA_TEXT2SQL_IMPL` 开关），**没有 `required_columns`**，也不看图表需要哪些列。
3. 图表由另一次 LLM 看查询结果生成，洞察由 code wizard 写 Python，最后写作、评分、最多 3 轮修改。

`rpt-09` 里发生的事：规划把"采购月报"套进销售向的大纲，问题写成"2026年9月报告期**已确认的采购金额和采购箱数**，按品类各是多少"。"报告期"、"已确认"是 `sales_reports` / `report_facts` 的词，采购单没有这个状态，查数时有的查询按动销表去找，回答里就出现"9 月无确认采购"。另一条查询其实查到了按品类的采购箱数（`purchase_cases`），但列名既不是 `quantity` 也没进图表的数据集，判分也没有 `quantity` 的别名表。

## 开发集之后的修改（尚未重跑）

- `t2s-15`：ReAct 提示的聚合规则改为"计数、求和、求平均、求占比或比较时，在 SQL 里直接算出最终结果列；占比同时返回分子、分母和比例"，旧方案的 SQL 提示换成**同一句话**，以新方案为准。
- 报表规划提示（`REPORT_QUESTIONS_PROMPT`）加两条：口径跟用户点名的一致（采购用下单时间、采购单状态、箱数、金额，不用"报告期""已确认"）；图表需要的度量逐项写进同一条问题，并写明分组维度。
- `t2s-25` 重做：原题在"有用户、没订单"的合作关系上问"每个用户下了多少张"，两边都把"用户"当成 `distributor_id`，结果为空所以碰巧答对。`purchase_orders` 没有用户列，改到有订单的 `ps-liancai-01` 上问，诚实的回答是"无法按用户拆分"，且不能出现经销商的总单数 33。
- `t2s-31` 新增（并列题）；`score_golden.py` 给 `quantity` 加了列名别名（`purchase_cases`、`total_boxes` 等），与 `line_total` 一致。
- 提示词两边都变了，所以开发集需要重跑（至少 `t2s-15`、`t2s-25`、`t2s-31`、`rpt-09`，最好整套开发集），之后才跑留出集。

## 用户归属口径更正

ORM 里有 `users` 和 `sessions.user_id`，但 `purchase_orders` 没有用户归属字段，当前订单也没有通过 session 关联到用户。采购单的业务归属是 partnership/distributor；Text2SQL 不开放 users/sessions，避免把工作台用户误当成下单人。`t2s-25` 因此改为经销商维度对照题：“这个经销商一共下了多少张采购单？”，seed_v2 的金标是 67。

### 关于「500 条和 50 条延迟差不多」

P50 / P95 / P99 是**每一条请求自己**从提交到收到回复的耗时，不是整轮总时长。并发固定为 5、worker 也是 5，任何时刻最多 5 条在飞，没有排队，所以每条仍约 5s，与总条数无关。总时长才随条数增长：50 条约 1 分钟，500 条约 8.9 分钟。

因此 A1→A2 加条数是验证**稳态是否漂移、尾部是否变坏**，并让 P99 有足够样本；它**不会**让单条变快或变慢。想找吞吐上限，要改 `--concurrency` / worker 数，那是另一组实验。

## 关键发现：省钱

1. **修复 Qwen async stream 后，问候路径不再因 Qwen 失败而 fallback 到高峰期 `deepseek-flash`。** 同样 50 条工作量：S3 r2（修复前）¥0.076858 → S3 r3（修复后）¥0.014747，**降低 80.8%**；单条请求约 ¥0.00154 → ¥0.00030。DeepSeek 高峰价输入 ¥2.00/M、输出 ¥8.00/M，Qwen 为 ¥0.20/M、¥0.80/M，每次误降级贵约 10 倍。
2. **隐式缓存已在起作用（未开显式缓存）。** `chat` 命中率稳定 76%–80%（A1 r2 76.4%、S3 r3 79.6%、A2 78.7%），总花费比无缓存原价省 **53%–55%**（A2：¥0.1514 vs ¥0.3265）。`open` 标题调用 prompt 短且几乎不命中（约 8%–20%），占总成本约 30%。
3. 按 A2 实测单条 ¥0.000303 推算，A3（2000 条）预计约 **¥0.61**。

价格出自 `backend/llm/pricing.py`（2026-11-09 核对的官方单价），费用由 `usage_records.estimated_cost_cents` 与压测脚本汇总；DeepSeek 分高峰/空闲价，Qwen 分三档阶梯价，输入、缓存命中输入、输出按各自单价计，不是统一单价。

## 结论

1. **A2 通过**：500/500，P50 4.9s / P95 6.5s / P99 7.2s，账本零失败、零残留 queued，无连接抖动。
2. A1 r2 的 P95 11.8s 是 50 条里 3 条尾部拉的小样本噪声；样本量到 500 后 P95 回到 ~6.5s，与 S2/S3 同量级，**P99 可信**（成功 ≥300）。
3. 吞吐约 0.93 条/s 受 `--concurrency 5` 与单条 ~5s 决定（5 / 5s ≈ 1/s），**不是**闸门或队列瓶颈；不要据此加 worker。
4. 成本观察：单次 Qwen 调用 prompt 约 **1.05k/次**、completion 约 **10/次**；得益于 `chat` 路径 **78.7%** 的隐式缓存命中率（命中部分按 20% 即 ¥0.04/百万计费），500 条压测总花费仅 **¥0.1514（约 1.5 毛钱）**，比无缓存原价（¥0.3265）节省 **53.6%**。问候场景输入远大于输出，仍是实验 C 上下文精简的候选，本轮只记录不改。
5. 下一步：**A3（2000）** 把 P99 报稳；约 36 分钟、约 6000 次 Qwen 调用，预计花费约 **¥0.61（约 61 分钱）**。

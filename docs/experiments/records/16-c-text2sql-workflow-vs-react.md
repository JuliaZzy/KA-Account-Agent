# 实验 C：text2sql 旧 workflow 与 ReAct 的结构对照

- **目的**：在其余条件尽量一致时，只比较结构（固定流水线 vs ReAct 循环）。B1 的 33/36 是旧提示词、旧结果视图下的数字，不能和 B2 直接比。
- **旧方案**：`backend/text2sql_legacy/`，选表 → 写 SQL → 失败重写（最多 3 次）→ 反思打分（80 分及格，最多 3 次）。
- **切换方式**：`KA_TEXT2SQL_IMPL=legacy`（`compose.yaml` 注入，默认 `react`），只影响 `data.query` 工具。规划、其余工具、回答阶段完全相同。
- **数据集**：`t2s-01`～`t2s-12`，每条 3 次，并发 1，种子 `seed_v1`；硬检查判分，没有 judge。三轮都在北京时间 22 点之后，同属非高峰价。

## 一致的部分

模型（DeepSeek flash，温度 0）、模型调用上限（10）、`sql_validator`（LIMIT 与 `system_row_cap`）、`prompt_view`、`no_matching_records`、结果过大时的重写提示、`required_columns` 检查、日志与打分落库、SQL 规则（`COALESCE`、产品名称加 SKU、长文本等）。`PICK` 里写死的"哪张表放什么"已去掉，旧版 SQL 提示里更细的产品规则已精简到与 ReAct 相同。

## 结果

| | 通过 | P50 | P95 | 模型调用/次 | ¥/次 | 备注 |
|---|---|---|---|---|---|---|
| 旧方案 v1（有缺陷，仅留档） | 28/36 | 11.80s | 16.91s | 6.06 | 0.00228 | 写 SQL 看不到 `required_columns` |
| **旧方案 v2** | **32/36** | 10.30s | 18.89s | 5.53 | 0.00201 | 补上 `required_columns` 与重写时的原问题 |
| **ReAct** | **35/36** | 10.79s | 13.85s | 5.28 | 0.00438 | 代码同 r5 |

失败用例：旧 v1 `t2s-02/10/11/12`；旧 v2 `t2s-11`（3 次）、`t2s-12`（2 次）；ReAct 只有 `t2s-12` 第 2 次。

## 对照过程中发现的不对等

v1 的 8 次失败里 7 次是"缺少必要字段"：ReAct 从第一步就能看到 `required_columns`，旧方案的写 SQL 步骤看不到，第一版 SQL 列名（如 `total_purchase_amount`）与下游要求的 `total_amount` 不一致，重写时又没带原问题。这是**信息量不对等，不是结构差异**，已修（`_write_sql`、`_revise_sql`），v2 是修复后的结果。

## 观察

1. **最干净的差异在 `t2s-11`。** 旧方案 3 次都答错：答"6 张"、"7 张"，或"没有数据"（用 `created_at`、`eta_date` 或事件表各猜了一个"完成日期"）；ReAct 3/3 通过。这类"口径不确定，需要看结果再调整"的题，正是循环该有的优势，但只有一道题，需要更多这类题才能下结论。
2. **`t2s-12` 两边都不稳定。** 旧方案的失败里有 `query is too deeply nested`（校验器的嵌套深度限制）与缺列；ReAct 第 2 次缺列。这不是结构差异，是 SQL 写法加校验限制，值得单独看。
3. **成本是 ReAct 的主要代价。** 数据查询部分每次约 ¥0.0040，旧方案约 ¥0.0016，约 2.5 倍。ReAct 每次约 3.3 次循环调用、每次 2544 token，缓存命中 63%（r5 是 79%，本轮偏低，见"局限"）。旧方案各步 prompt 短，缓存命中约 80%。
4. **延迟差别不大。** P50 10.79s 对 10.30s，ReAct 的 P95 更好（13.85s 对 18.89s），因为旧方案失败时多轮重写、反思会拖尾。
5. B2 之前记录的"P50 快 32%"主要来自合并步骤；对齐信息量后差距基本消失。

## 局限

- 36 次是一次运行，`t2s-11` 的差距（0/3 对 3/3）与缓存命中的差别都有随机成分；两种方案之间的通过率相差 3 次，没有重复就不能算显著。
- golden 里能区分两种结构的题很少（基本只有 `t2s-11`），其余题第一次就能写对。
- 提示词里的 SQL 规则最初是针对 ReAct 在这批题上暴露的问题补的，旧方案补的是同一批规则，但没有再针对旧方案的失败调过提示，这对旧方案略不利。

## 结论（暂定）

- 在这批题上，ReAct 比旧方案好 3 题（`t2s-11`），成本高约 2.5 倍，延迟持平。
- 现在只能说 ReAct 在"需要根据结果调整口径"的题上有优势，不能说它整体更好。
- 下一步需要更多会让第一次 SQL 出错的题（类型错误、列名歧义、空结果需放宽、超过 200 行需聚合、缺必需列），每类 3～5 题，再配合 ReAct 的消融（关闭自检打分、限制重写次数）看成本值不值。

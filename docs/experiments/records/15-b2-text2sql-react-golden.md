# 实验：B2（仅 Text2SQL）— ReAct 查数循环 vs B1 旧流水线

- **目的**：text2sql 从"选表 → 生成 SQL → 打分"换成 ReAct 循环，并加入 `columns` 校验、截断标记、结果触顶让模型改写之后，先单独看这条路径有没有退步，再决定要不要完整重跑 B。
- **日期**：2026-11-11（UTC）
- **数据集**：`golden_v1.jsonl` 的 `t2s-01`～`t2s-12`，每条 3 次，并发 1（与 B1 相同）；种子数据 `seed_v1`（495 张采购单）。判分口径沿用 B1 修订后的版本，只有硬检查，没有 judge。
- **模型**：Qwen `qwen3.7-flash` + DeepSeek `deepseek-flash`，Docker Compose 全栈，worker 5。
- **只测了 Text2SQL**，没有测报表、合同、采购、安全，所以**不能**替代完整的 B。

## B2-r1 的两个问题

1. **规划把 data 当成工具，整个请求失败（6/36 次）。** 注册的工具只有一个，叫 `data.query`（就是 text2sql agent）。规划里 `kind:"agent", name:"data"` 会被 `tool_name_for` 映射成 `data.query`；模型有时写成 `kind:"tool", name:"data"`，运行时就去找一个名叫 `data` 的工具，找不到，报 `unknown tool data`，回答"查询失败"，一条 SQL 都没跑。根源是规划提示里有两层命名（agent 别名 `data`、工具函数名），模型偶尔混用，**不是存在第二个 data 工具**。**B1 的 113 次运行原始 trace 里 `unknown tool` 出现 0 次，所以这是 B1 之后引入的退步**（规划提示里加了 `deliver`/`columns` 的要求，同时 ReAct 改动期间提示结构变了，具体是哪一条触发的没有单独验证）。
   - 临时修法：解析时 `kind=tool` 但名字是 agent 别名，就按 agent 处理。
   - **根治（r5 之后做，r5 的 36/36 是在临时修法上测的）**：规划输出里不再有 `kind` 字段，agent 的名字统一带 `_agent` 后缀（`po_agent`、`data_agent`…），由代码按名字推导 `kind`；带 `_agent` 但不认识的名字当作未知 agent 丢弃，而不是当工具派发。旧计划里残留的 `kind` 只用来拒绝非法值，不再决定类型。**这一改动尚未用真实模型测过**，规划提示的名字变了，需要在下一次 36 条里确认 `tool:data` 仍是 0。
2. **`COALESCE(SUM(x), 0)` 把"没有记录"写成"金额 0.0"（`t2s-08/09/10`，8 次）。** B1 的 SQL 是裸 `SUM`，空结果为 NULL，回答说"数据为空"；ReAct 模型习惯补 0，于是 `t2s-10`（这个合作关系根本没有订单）答"去年采购总金额为 0.0"。这是**准确性退步**，不是判分问题。修法：ReAct 提示禁止用 COALESCE 补 0、需要时同时返回 `COUNT(*)`；修完后 SQL 变成 `SUM(...), COUNT(*)`，但回答模型仍会把 null 说成 0（r2 残留的 2 次），再在回答提示里加一条。

## 延迟与成本（成功运行，每次 36 条的汇总）

| | B1 | B2-r1 | B2-r2 |
|---|---|---|---|
| 端到端 P50 | 12.83s | 9.27s | 9.79s |
| P95 | 17.88s | 14.83s | 16.83s |
| 模型调用/次 | 5.1 | 4.67 | 5.14 |
| 单次成本（账本，按当时时段计价） | ¥0.00132 | ¥0.00406 | ¥0.0047 |
| **单次成本（统一按非高峰重算）** | **¥0.00132** | — | **¥0.00254** |

- **延迟变好**：P50 降约 3 秒。ReAct 的单次调用只有 ~1 秒（输出很短），比旧流水线每步 2～3 秒快。
- **成本变差，约 2 倍**，原因是 `data.react` 每次请求 3.1 次调用、每次约 2500 个输入 token（旧流水线 `data.sql` 约 1340）。缓存命中率 86%～92%，已经很高。
- **账本数字不能直接比，要注意计价时段。** DeepSeek 工作日北京时间 9–12、14–18 点输入输出价格翻倍（`pricing.py`）。B1 在北京时间 18:08 开跑（非高峰），B2 在 17:20～17:50 开跑（高峰），所以账本里差 3.5 倍，统一按非高峰重算后是约 2 倍。**以后实验要记录开跑时段，或统一用同一档价格重算。**
- 汇总里 r1 的 4.67 调用/次受 6 次"工具失败"（只有 2 次调用）拉低，不可比；r2 的 5.14 才是正常口径。

## 已处理（r4/r5 验证）

- **`t2s-12` 在 r5 里 3/3 通过**：回答提示加了"比较、变化、占比类问题把参与比较的每个原始数字和结果一起写出来"，答案变成"9 月 6731.82，8 月 7405.53，减少 673.71，约 -9.1%"。
- **"没有数据"规则收紧**：只有记录数为 0 或没有行才说"没有数据"；汇总值为 null 但记录数大于 0，说明记录存在而字段为空，如实说。没有记录数可看时，null 仍按没有数据处理。
- 36/36 是**硬检查**口径，`t2s-09` 有一次回答只有"没有数据"四个字，没带月份，硬检查通过但信息偏少，judge 项没有跑。

## 以下是 r2 时的遗留（其中 t2s-12 已在 r5 解决）

- **`t2s-12`（9 月比 8 月变化多少 / 百分比）仍 1/3 通过（r2）。** 旧流水线里它因 `ROUND(double precision, int)` 报错 0/3；ReAct 版本不再报错，SQL 和计算都对（-673.71、-9.1%），但 2 次答案只写差值和百分比，没写 9 月、8 月各自的金额，而判分要这两个数。是**答案太简略**，不是查错，**没有处理**，也不应该为了判分把"回复要短"改掉；要么放宽这条用例的判分，要么在提示里要求"比较类问题列出对比的两个数"，这是产品决定。
- **成本 2 倍**：`data.react` 每步都重发完整目录和历史观察。可以试：精简目录、把 schema 观察只留最近一次；这是实验 C 的候选，**未验证**。
- **"没有数据"改由代码判定（r5 之后做，未实测）**：统一视图 `prompt_view` 新增 `no_matching_records`：无行，或单行里所有值为 NULL（或 count 列为 0）时为真；真实的 0 金额、记录存在但字段为空都不会被标记。回答提示只需读这个标记，不再各写一遍"null 说成没有数据"的规则。
- **成本还没降。** 评估过三个办法，**都没有照原方案做**，见下一节。

## 结论（r5 之后）

1. **最终代码上 text2sql 36/36（B1 33/36），P50 8.74s（-32%），成本 1.6～2.6 倍。** 通过率提升有一部分来自提示词针对这批用例补的规则（没有数据、比较类要写两个数），**这是在评测集上看到问题再改的，存在过拟合风险**，需要在没见过的问题上验证。
2. 下面是 r2 时的结论，保留作为过程记录。
3. ReAct 版 Text2SQL 修完两个问题后，通过率回到与 B1 接近（r2 32/36，B1 33/36），**P50 更快（约 -3 秒），成本约 2 倍**。
2. 第一轮 22/36 是真实退步，来自两个具体、可修的缺陷，而不是评测噪音；其中规划 `kind` 误填会让整个请求失败，值得单独记一笔。
3. 样本只有 12 条 × 3 次，r2→r3 之间还有未全量复测的修改。**要把它作为后续实验 C 的 text2sql 基线，需要在最终代码上再完整跑一遍 36 条。**

## 降成本的评估（只做了估算和分析，没有改代码、没有跑）

`data.react` 的成本构成（r2，非高峰价）：**未命中缓存的输入 64%、输出 30%、命中缓存的输入 6%**；每次调用平均 437 个未命中 token、2077 个命中、52 个输出。所以"压缩单次输入"没用，缓存前缀几乎免费；要降只能减少调用次数或每步新增的内容。

1. **把列信息放进缓存前缀、去掉 `inspect_schema`**：元数据共 264 个列，渲染后估算 1 万 token 以上（现在整个提示约 2500），是**估算，没实测**。命中时每次调用多约 ¥0.00024，3 次里省 1 次调用约 ¥0.0007，净省很少；一旦缓存没命中，单次调用就是约 ¥0.012，比现在一整次请求还贵。还会把 `inspect_schema` 这个 ReAct 工具拿掉。**不划算，除非流量大到缓存常热**。
2. **schema 观察只留最近一次**：旧观察在缓存前缀里，只占成本 6%，删掉还会破坏前缀缓存。**不做**。
3. **真正的杠杆是第 3 次调用**（`finish` + 打分）：r5 里 36 次中 30 次正好 3 次调用，6 次多于 3 次（循环确实起了作用）。对"干净"的结果（单行聚合、列齐全、未截断）由代码直接结束，能省约 1/3 的调用，但这就是 ReAct 的自检环节，**要做就必须先做消融实验**，见下。

## 怎么体现 ReAct 的优势（待你定）

现有 12 条几乎都是一条 SQL 就能答的问题，ReAct 的自修复、观察后重查没有被测到，所以只看到成本和延迟。要比较，需要**第一条 SQL 容易写错**的用例，例如：类型错误（`ROUND(double, int)`）、列歧义、空结果需要放宽条件、结果触顶需要改聚合、`required_columns` 缺列。对照组是"单次生成、不看结果"，比较通过率和成本。这些用例目前不在 golden set 里。

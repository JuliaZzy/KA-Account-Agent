# 记录 27：C 改前补账——前四节正文的 token 与费用

接记录 25 / 26。产品代码未改。五份完整月报（`rpt-01` / `plan-02`，rptfix 冒烟 + D Worker=5）的 Run 树里，前四节正文（关键指标、业绩表现、库存情况、下一周期计划）都跑过，但 `_write_section` 没带 `trace`，vendor usage 没进账本。C 的「改前」数字必须把这四次补上，否则后面「合并调用」会看起来像假降。

账本里只有「问题与风险」那一次正文。用同一套组包函数还原前四节的 prompt，再用这次已入账调用上的 **vendor token / 本地估计** 比例折算。费用按 DeepSeek flash 非高峰价：命中 ¥0.02 / 未命中 ¥1.00 / 输出 ¥4.00，每百万 token。

明细：`docs/experiments/exports/report-ledger-breakdown.json`、`report-missing-writes.json`。还原脚本：`docs/experiments/golden_set/reconstruct_missing_writes.py`。

## 方法

1. 从 `report.plan`、各 `data` child 的 payload、出图结果、首轮审阅证据里的洞察和新闻，按 `_section_payload` / `WRITING_PROMPT` 重组 prompt。
2. 正文取**首轮审阅**里的章节（修订前的草稿）。`rpt-01#3` 的库存情况当时只有两行图表引用（42 字），修订后才补上正文——漏记的是写的那一次，不是修订后的篇幅。
3. 同一 Run 里已入账的「问题与风险」存了完整 `request_json`。`rpt-01#1` 上，还原出的风险节 prompt 与账本原文的本地估计 **正好 1.000**。前四节没有「已写章节」块，所以折算用的是这次调用的 vendor/估计比（约 1.15–1.18），不把风险节多出来的前文摊进前四节。
4. 缓存：关键指标按冷启动（命中 0）；后三节按风险节实测命中（640）。四节全冷会再贵约 ¥0.002，可忽略。
5. 耗时仍无法从账本还原。风险节实测 3.7–5.1 s，四节串行大约 15–20 s 模型时间，已经算进端到端墙钟。

## 给实验 C 的改前数字

- **完整月报一次：约 22 次 `report` 调用，整棵树 ¥0.22–0.29，墙钟 2–2.5 分钟（单跑）或 3–4 分钟（D 的带排队样本）。**
- 账本里的 16–18 次、¥0.20–0.27 **少算了四节正文**。合并章节调用时，对照请用本表的补后数字。
- 漏记本身是记账缺口，不是少跑。墙钟已经包含这四次，改记账不会缩短延迟。

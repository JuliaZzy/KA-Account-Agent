# 实验：A3 r3 — 补投先看队列深度 + 标题 worker 并发 3 后的 2000 条复测

- **第几次**：A3 的第 3 次（[`r1`](11-a3-greeting-2000.md)、[`r2`](12-a3-r2-greeting-2000.md) 之后）。命令、模板、并发、租户分布与 r1/r2 完全相同
- **日期**：2026-11-10 UTC 08:22:10–08:59:34（约 37 分钟）
- **代码**：相对 r2 只改了两处——补投前先看目标队列在 Redis 里的深度；title-worker 并发 2 → 3
- **原始文件**：[`exports/load-test-greeting-a3-2000-r3.json`](../exports/load-test-greeting-a3-2000-r3.json)、[`exports/load-test-greeting-a3-2000-r3.log`](../exports/load-test-greeting-a3-2000-r3.log)

## 目的

验证 r2 暴露的补投缺陷已修：标题队列不再积压，没有重复消息，没有健康 Run 被误判失败，且 r1 / r2 已修的内容没有回退。

## 结果

| 指标 | r1 | r2 | **r3** |
|---|---|---|---|
| 请求 / 成功 / 超时 | 2000 / 1998 / 2 | 2000 / 2000 / 0 | **2000 / 2000 / 0** |
| 成功 P50 / P95 / P99 | 4.62 / 6.02 / 7.38s | 5.09 / 7.69 / 10.71s | **5.01 / 7.61 / 9.74s** |
| 成功 max | 73.67s | 19.07s | **23.72s** |
| 对话 Run 排队 p50 / p95 / max | ≈0 | 0.01 / 0.01 / 0.11s | 0.01 / 0.01 / 1.30s |
| **标题 Run 等待** p50 / p95 / max | 145 / 343 / 366s | 244 / 481 / 487s | **0 / 2 / 7s** |
| `open` Run 终态 | 1998 成功，**2 个 chat 永远 queued** | 1967 成功、**24 失败**、9 个未完 | **2000 全部成功** |
| `run.requeued_by_sweeper` 事件 | 0 | **3083** | **0** |
| `redispatch_count` 非 0 的 Run | — | 大量（3 的有 598 个） | **0** |
| 死信 | 0 | 24（误杀） | **0** |
| 花费 / 单条 | ¥0.5741 / ¥0.000287 | ¥0.5703 / ¥0.000285 | **¥0.6057 / ¥0.000303** |

整体：4000 个 Run（2000 chat + 2000 open）**全部成功**，补投机制全程没有触发（没有消息丢，也没有被误当成丢）。库里没有任何 `queued` / `running` 的残留。

### 标题队列为什么不再积压

r2 的原因是 title-worker 并发 2 时吞吐约 0.8 条/s，追不上对话约 0.95 条/s 的完成速度。并发调到 3 后标题调用约 2.5s 一个，吞吐约 1.2 条/s，标题 Run 创建后平均 0 秒就被领走，最长 7 秒。两个修复缺一不可：只改并发，积压以后换个负载还会出现；只改补投，积压本身（容量）仍在。

### 成本为什么回到 ¥0.000303

`open` 的 Qwen 调用从 r1 的 1690 次、r2 的约 1660 次升到 **1996** 次，也就是几乎每个标题都精修了，单条 `open` 成本 ¥0.000091，总单条回到与 A2 一致的 ¥0.000303。r1 / r2 少的那部分是因为标题 Run 在排队很久后被「负载下放弃精修、保留临时标题」跳过，r3 没有积压，所以几乎不跳过。这个解释与数字吻合，但**没有单独验证「跳过的具体次数」**，不当作确凿结论。

### 连接与 Qwen 尾部

- **连接**：压测结束后（按容器 IP 对应服务）worker 5 个空闲连接、title-worker 3 个、sweeper 1 个、API 5 个，合计 14 个，远低于 97；没有 `too many clients`（r1 修复前 worker 一个容器就占 27 个）。
- **Qwen 失败 2 次**，都是 `APIConnectionError`（`PROVIDER_NETWORK`），耗时 11 秒和 18 秒后才报错，都 fallback 到 DeepSeek 成功，共 2 次 DeepSeek。这两次是连接错误而不是我们设的 30 秒 / 10 秒超时：Qwen 单次调用最长成功 15.4 秒，没有到上限。所以**这轮没有机会验证超时是否真的会触发**，它只被单测验证过（见 `tests/test_llm.py`）。
- 流式事件跨度 `reply_updated` 平均 0.09 秒、最大 1.11 秒，与 r2 一致。

### P50 / P95 / P99 比 r1 慢，是什么原因

r3 的 P50 5.01s 与 r2 的 5.09s 几乎一样，都比 r1 的 4.62s 高。按步骤看：

| 步骤中位数 | r1 | r2 | r3 |
|---|---|---|---|
| `orchestrator.plan` | 2.20s | 2.40s | 2.38s |
| `orchestrator.answer` | 2.10s | 2.23s | 2.18s |
| Qwen 单次调用 p50 | 2143ms | 2300ms | 2275ms |

r2 和 r3 是相隔约 1 小时的两次独立运行，数字一致，所以**不是一次性抖动**；变慢全部出现在 Qwen 调用内部，对话排队仍 ≈ 0。但是否来自供应商时段负载（r1 在北京时间 11:33，r2 / r3 在 15:24 / 16:22），还是来自 r1 之后我们改的代码（超时包装、流式逐块触发 `on_text`、`Database` 复用、连接池），**这三轮无法区分**。想分清，需要在同一时段用旧代码对照跑一遍，或者直接用同一个脚本直连 Qwen 测同样的调用，成本很小。这个差异（约 +8%）远小于 r1 里的 73 秒尾部，暂时不阻塞，但记在这里，不当作「没有影响」。

| 补投误把「在排队」当成「丢了」（r2 新发现） | 0 次补投、0 个误杀、标题等待最长 7s |

## 结论

1. **A3 在 2000 条规模下 100% 完成、无残留、无误杀**，补投机制只在真的需要时才动（本轮 0 次）。
2. 修好的内容中，**重试（DB 连接失败）和超时这两项没有被真实压测触发过**，只有单测证明；它们靠的是「没出事」而不是「出了事被接住」，不要在简历或汇报里说成已在压测中验证。
3. 吞吐与延迟基线更新为 r3：P50 5.01s、P95 7.61s、P99 9.74s，约 0.9 条/s，单条 ¥0.000303。比 r1 慢约 8% 的原因未区分，已记录。
4. 一条值得讲的经验：**修一个 bug 时引入的修复本身要被同一批压测检验**。r2 里补投逻辑刚修好就在标题队列积压下自我放大，是因为单测没有「深队列」这种形状的数据。

## r3 之后的代码变更（没有重跑 A）

r3 记录之后，sweeper 补投路径和压测脚本又改过几处。**A 的数字不受影响，没有重跑**：A 测的是「API 入队 → outbox → Celery → worker → 模型 → 写库」，而下面的改动在 sweeper 补投和压测脚本上；r3 里补投一次都没有被触发（0 次 requeue），所以它没经过这些改动过的代码。

| 改动 | 说明 |
|---|---|
| 补投逐条领取、逐条发布 | 发布失败只回滚这一条的补投计数；`purge_dispatched_outbox` 也改成先在库内过滤再 `LIMIT`（和 A3 r1 的「先限量再过滤」同一类问题） |
| 超龄策略 1h → **2h 自动失败** | Codex 一度把超龄改成「保持 queued 等人工」，与「历史数据走正常流程处理、不手工改库」的要求冲突，已改回自动关闭（`STUCK_QUEUE_EXPIRED`），阈值 2 小时（`KA_ACCOUNT_QUEUED_MAX_AGE_SECONDS=7200`）。判定不依赖 Redis。记录 11、12 里写的「1 小时」是当时的真实行为，不改 |
| SoftBusy 重试打心跳（迁移 `0027`） | `self.retry` 把任务当 ETA 消息放在 worker 内存里，Redis 队列读到 0 而 Run 其实在合法等待；不处理的话，过载时（实验 D）会被当成丢失去补投，等久了还会被超龄关闭。现在每次重试前写 `agent_runs.queue_heartbeat_at`，补投和超龄按 `queued_at` 与心跳较晚者判断；`queued_at` 不动，监控里的排队时长仍是真实的 |
| `scripts/load_test_chat.py` | 每个请求记 `run_id` 和结果分类（completed / client_timeout / enqueue_error / poll_error）；超时后有界跟踪本实验的会话但不取消；费用在跟踪快照之后汇总并标记快照是否完整；新增开环模式 `--arrival-rate` / `--max-pending`（给实验 D）。延迟与完成率口径没变；20 条真实小冒烟 20/20、P50 4.58s、P95 6.77s、¥0.000314/条，与 r3 一致 |

验证：全部测试通过；心跳与超龄新增 6 个 Postgres 回归测试（含「心跳新鲜的 5 小时老 Run 既不补投也不超龄」「心跳停了 3 小时的 Run 照样超龄」「Redis 读不到时孤儿仍被关闭」）。

仍然成立的限制：**「队列空 + 补投耗尽」只能说明这条消息现在不在 Redis，不能证明消息丢了**（worker 预取、延迟重试都可能让它不在队列里）。心跳补上了 SoftBusy 重试这一类；其他延迟重试（DB 连接失败重试最多 5 次、约 2 分钟内）靠 120 秒宽限期覆盖。

# 实验总结

记录 01–33 里碰到的问题、处理方式和处理后的结果。数据都是合成种子（`seed_v1` / `seed_v2`）上的实验室运行，不是线上流量。问候压测只看链路通不通；质量数字来自金标硬检查，没有 LLM-as-a-Judge。DeepSeek 价格后来固定按低峰价重算，跨记录比成本时以重算口径为准。

## 运行时：问候压测（记录 01–13）

**闸门打满时 Celery 把任务 ACK 掉，Run 永远停在 `queued`。** 同一用户并发 5，每条问候再挂一条标题 Run，瞬时申请超过 `GATE_USER=5`。`acquire_run` 失败只返回 `False`，任务被当成成功结束，outbox 停在 `dispatched`，模型一次都没调。当时 sweeper 还连不上 Postgres（容器 Up，DNS 解析 `postgres` 失败），补投也断了。10 条里 2 条打满 180 秒超时，完成率 80%。

处理：领不到座位或队列关闭时抛 `SoftBusy`，Celery 重试而不是 ACK；标题改投独立队列 `ka_account.title`，不再占聊天座位；sweeper 增加 Postgres `select 1` 探活。

效果（记录 02，同一模板、并发 5）：10/10，0 超时。P50 从 9.31 秒降到 4.07 秒，观测最大从 180 秒降到 12.45 秒。chat 和 open 都没有残留 `queued`。

**多用户、多组织把这条链路再放大。** 没有新的卡死。单组织 3 用户 20/20（记录 03），P95 从单用户的 12.45 秒降到 6.77 秒。跨两个经销商 50/50（记录 04），但 P95 被 3 条 35–43 秒的尾巴拉到 35.22 秒。

**这 3 条长尾被记成 `PROVIDER_NETWORK`，实际是本地把 async 流当成同步迭代。** Qwen 返回 async generator，`_assemble_stream` 用 `for chunk in chunks`，抛出 `TypeError: 'async_generator' object is not iterable`，再被兜底标成网络错误，走退避后降级到高峰价 DeepSeek。补上 `cause` 之后才看见真实异常（记录 05）。中途还试过拆成两次 `asyncio.run`，流还绑在已关闭的 loop 上，变成 `Event loop is closed`。

处理：在同一次持久 event loop 里把流拉完再交给同步组装；这类 `TypeError` / `RuntimeError` 改记 `PROVIDER_BAD_RESPONSE`。

效果（记录 06，同一 50 条多组织）：P95 从 35.22 秒降到 8.79 秒，最大从 43.46 秒降到 9.81 秒。Qwen 失败 0。50 条花费从 ¥0.0769 降到 ¥0.0147，降 80.8%，因为不再误降级到高峰价 DeepSeek。

**A1 第一次的 P95（76.6 秒）是出站闪断，不是代码。** 同一秒 Qwen 和 DeepSeek 一起 `APIConnectionError`，当时本机在切 VPN。没有改代码，同配置重跑（记录 08）：50/50，P50 4.92 秒，P95 11.80 秒，0 次连接失败。基线取这一轮。

**500 条和 2000 条稳态没有漂移。** 记录 09：500/500，P50 4.91 秒，P95 6.46 秒，P99 7.18 秒，Qwen 失败 0，单条 ¥0.000303。记录 11 的主体同样健康（成功样本 P50 4.62 / P95 6.02 / P99 7.38 秒），但 2000 条里有 2 条超时。

**2 条超时是连接尖峰加上补投扫描永远看不到新的卡住 Run。** 那一秒 Postgres `max_connections=100` 被打满，`execute_run` 抛 `too many clients` 后消息已经算出投递。sweeper 的 `unclaimed_dispatches` 先 `ORDER BY dispatch_at LIMIT 100`，再在 Python 里过滤「Run 仍是 queued」。历史 `dispatched` 行有 6208 条，最老的 100 条对应的 Run 早就成功了，过滤后是空的。这两条卡在排序的第 3271、3273 位。另外每个任务都 `Database()`，新建引擎和连接池，空闲 worker 占着 27 个连接、最老近 3 小时，把余量吃掉了。

处理：补投改成以 `agent_runs` 为主表，库内先按 `queued` 过滤再 `LIMIT`，`FOR UPDATE SKIP LOCKED`，同事务增加补投次数；排队超过时限的历史 Run 直接 `STUCK_QUEUE_EXPIRED` 并写死信，不重放、不调模型；`execute_run` 遇到 `OperationalError` 做带抖动的重试；每个 worker 子进程只建一次 `Database`；各服务连接池按预算封顶（合计 85，低于应用可用的 97）；终态 Run 超过 7 天的 `dispatched` outbox 分批删除。

效果：迁移后第一轮 sweeper 把库里 71 个历史 queued Run 全部关掉，`model_calls` 总数不变，零模型调用。worker 空闲连接从 27 降到 5。

**修补投时用固定宽限期区分「消息丢了」和「还在排队」，把健康的标题 Run 误杀了。** 标题 worker 并发 2，吞吐约 0.8 条/秒，追不上对话约 0.95 条/秒。超过 120 秒就再投一份，队列里其实还有原消息，于是自我放大。记录 12：对话 2000/2000，但标题 Run 补投事件 3083 次，24 个被判 `STUCK_REDISPATCH_EXHAUSTED`，等待中位 244 秒。这些 Run 只是标题没精修。

处理：补投和「耗尽」之前先看目标队列在 Redis 里的深度，队列非空就不补投、也不判失败；聊天队列和标题队列分开看；读不到 Redis 时同样跳过，真丢了的由超龄关闭兜底。标题 worker 并发 2 调到 3。后来又给 SoftBusy 重试写 `queue_heartbeat_at`，避免 ETA 重试时 Redis 深度为 0、Run 却在合法等待。

效果（记录 13，同样 2000 条）：4000 个 Run（对话 + 标题）全部成功。补投事件 0，误杀 0，死信 0。标题等待从中位 244 秒 / 最长 487 秒变成中位 0 秒 / 最长 7 秒。

**修 async 流时把逐字输出缓冲掉了。** 为了避开已关闭的 loop，先把整段流收成 list，`on_text` 在收完之后才触发。一次 71 秒的 Qwen 调用里，8 条 `reply_updated` 挤在 16 毫秒内。

处理：在 async 循环里边收边喂给组装器。

效果：同一 Run 上回复事件的时间跨度从平均 0.01 秒变成 0.09 秒（短问候本身输出很短）。延迟数字不变，用户不再干等整句突然出现。

**Qwen 单次调用没有有效超时。** 默认 `timeout` 是 7200 秒。记录 11 里一次 ANSWER 调用 71 秒才返回，期间用户什么都看不到。

处理：单次总时长 30 秒，相邻 chunk 静默 10 秒，超时记为可重试的 `PROVIDER_TIMEOUT` 并降级。

效果：记录 12 最长成功调用 26.3 秒，记录 13 最长 15.4 秒，都没碰到上限。30 秒超时和数据库连接被拒的重试只有单测，压测里没有真的触发过。

**worker 重启后第一波慢约 3.5 秒，不是用户闸门，也不是缓存。** 记录 10 在同样 30 条、同样冷启动下对比单用户和三用户：第一波都是约 8 秒，之后中位约 4.5 秒。前缀缓存冷的时候单次模型延迟也不变，只是花费大约多 15%。多出来的时间在排队约 1.2 秒和模型调用之外的首次初始化约 2.5 秒。后来量过「每个任务新建引擎」大约 17 毫秒，排除了它是这 2.5 秒的来源。启动预热没有做。

## 评测集和评分器

**按原版词表判分，把说对了的「没有数据」判失败。** 记录 14：原版 58/113（51%），补上「没拿到 / 查不到」等说法、把跨租户的「查不到」从「必须明确拒绝」放开、以及 `8.0%` 能对上 `8%` 之后，是 76/113（67%）。多出来的 18 次全是口径放宽，agent 没有变好。标准答案抽查与种子库一致。

**合同问答的日期和加粗把评分器打断。** `2031 年 9 月 30 日` 的空格、`**不会** 自动续约` 的星号，内容是对的，子串匹配失败。

处理：匹配前去掉 `*`、反引号，以及汉字两侧的空格。回答里的格式不动。

效果：`con-qa-02` 重评 5/5；并发 5 的合同题修订后 24/24。

**`.env.example` 的 `GLM_BASE_URL` 指错了接口。** 合同入库返回 `input is required`。示例改到 layout parsing 的路径后，两份协议读回与标准答案逐字段一致。入库当时不进 `agent_runs` 账本，这份 OCR 费用没有数字。

**种子从 v1 灌成 v2 时，正在跑的开发集作废。** 订单 495 张变成 1349 张，金标仍按旧数据算。`golden-hard-dev2-*` 作废，金标用 `build_golden_v2.py` 重算。v2 里单个合作关系有 147–249 行明细，系统 LIMIT 100/200 会自然触顶，这是后面截断题能测到的前提。

## Text2SQL：固定流水线还是 ReAct（记录 15–19、23）

**ReAct 第一版退步，22/36，低于旧流水线的 33/36。** 两类问题叠在一起（记录 15）。

规划把 `kind:"tool", name:"data"` 当成一个不存在的工具，6/36 次整次失败，一条 SQL 都没跑。B1 的 113 次里 `unknown tool` 是 0 次，这是改提示之后引入的。临时处理：名字是 agent 别名就按 agent 派发。根治是规划输出去掉 `kind`，名字统一带 `_agent`，由代码推导类型。36/36 是在临时修法上测的；带 `_agent` 的提示之后的全量金标里没有再出现 `unknown tool data`。

模型用 `COALESCE(SUM(...), 0)` 把「没有记录」说成金额 0。处理：禁止用 COALESCE 补 0，结果视图增加 `no_matching_records`；只有 0 行才说没有数据。针对性的 9 次重跑 9/9。比较类问题只写差值和百分比、不写两个原数，补了一条回答规则。

效果：最终代码上 `t2s-01`～`t2s-12` 为 36/36（B1 是 33/36），P50 从 12.83 秒降到 8.74 秒。成本约是旧流水线的 1.6–2.6 倍，高峰价和缓存波动大，不能只引一个数。这 36 题大多一次就能写对，通过率里有针对失败补的提示，有过拟合风险。评估过把整份 schema 放进缓存前缀、只留最近一次观察、以及干净结果跳过自检，前两个不划算或会拆掉前缀缓存，第三个没做消融，都没有改。

**对照实验里旧方案第一版吃亏，是因为它写 SQL 时看不到 `required_columns`。** 8 次失败里 7 次是缺字段，不是结构差异。两边对齐之后（记录 16）：旧方案 32/36，ReAct 35/36。干净的差异只剩 `t2s-11`（口径不确定，要看结果再改）：旧方案 0/3，ReAct 3/3。ReAct 数据侧成本约 2.5 倍，P50 持平。

**困难题上，差距来自「第一次写错之后怎么办」。** 旧流水线只有报错才重写，空结果直接答「没有数据」；ReAct 看到空结果或类型错误会再查。`ROUND(double precision, int)` 在 Postgres 里不存在，旧方案对同一个报错重写三次仍修不好。

开发集上改过截断计数、聚合规则、用户归属和并列规则，所以有调参成分（记录 18）：ReAct text2sql 30/30，旧 workflow 24/30。差在两类：产品名带规格时旧方案把「Energy Drink 250ml」当成完整产品名，空结果后不再查；结果触顶时旧方案自己加 `LIMIT`，说成 200 行，ReAct 按代码给的真实总数（201）回答。成本约高 60%。P50 只快约 0.5 秒，价值在正确性，不在延迟。

留出集冻结代码后只跑一次（记录 19）：ReAct 27/27，旧 workflow 24/27。唯一拉开的是 `t2s-22`（名称放宽）3/3 对 0/3。负向对照（真的没有数据、不存在的产品）两边都是 3/3，没有过度放宽。prompt tokens 约 1.9 倍。没做的对照是：旧流水线只加一条「空结果后再写一次」能否追平。

和结构无关、但对照前必须先改掉的口径问题：

- `purchase_orders` 没有用户字段，两边都把经销商总单数当成「每个用户的单数」，硬检查还碰巧通过。Text2SQL 不再开放 `users` / `sessions`。`t2s-25` 改成「这个经销商一共多少张」，金标 67，两边 3/3。
- 系统触顶只告诉模型「到了上限」，不知道真实总数。触顶时额外跑 COUNT，`row_count` 返回总数并保留 `truncated`。这是代码契约，不是 ReAct 本身；旧方案在同一契约下仍会自己加 LIMIT。
- `deliver=answer` 的纯对话题被多余的 `required_columns` 拒绝。改为不再强制这些下游字段。
- 占比题把明细丢给模型心算，模型数错行。两边提示改成同一句：计数、求和、平均、占比在 SQL 里算出最终列。
- 报表取数自己用「报告期 / 已确认」这类动销词，采购单没有这个状态。报表规划提示改成跟用户点名的口径走。`rpt-09` 在 seed_v1 开发集两边都是 0/3，seed_v2 开发集两边都是 3/3。
- 下单月用 `submitted_at`，预计到货用 `eta_date`，写进列注释。B1 里同一个「9 月采购金额」查数和报表差出 3312.72 与 2697.29。

**规划器会改写用户没说的条件，text2sql 只是照做。** 「所有采购单」被写成「所有未完成采购单」。记录 23 的开发集里 `t2s-27` 因此 1/3（前一轮 3/3）。没有改，记为遗留。

记录 23 收尾：修复之后的全量金标 39/39，留出集（偶数题加 `rpt-08`，每题 3 次，未再用于调参）30/30。

## 金标上的业务失败（记录 14、20–23）

B1 修订后 76/113。稳定失败集中在报表、显式 SKU、`ROUND`、合同问答走了查数、以及删除请求被口头说成已执行。C5 在 seed_v2 全量金标上是 29/37，8 个失败是 `po-03`、`po-04`、`saf-01`、`saf-03`、`rpt-03` 到 `rpt-06`。

**单独要图时规划只调了查数，一张图都没有，回答却说图已经在右侧。** 月报会出图，但饼图按商品而不是品类，无数据的月份仍画旧月份的图。

处理：回答只有在 `charts_drawn` 非空时才能说图已附上，否则明确说没能生成。查数成功后走轻量出图；规划漏写 `chart: true` 时用画图关键词兜底，已有月报任务时不兜底。图失败不把查询打成失败。

效果：冒烟里 `rpt-03` 到 `rpt-06` 各 3/3，12 次都出了图。兜底之前 `rpt-06` 有一次漏写 `chart`，回答诚实说没能生成柱状图。C7 报表从 3/7 变成 7/7。C5 的 8 个失败在 C7 全部通过。

**点名别的经销商时，会把当前合作关系的数答成对方的。** 先写进回答规则，冒烟仍有 1/3 漏说。再把判断挪到代码：用户原话命中其他合作关系的经销商名或品牌名时，在 `scope` 里写 `user_named_other`。评分词表补上「看不到」「只能查看」。

副作用：规则收紧前，用户没点名别人也会偶尔加上「我只能查看……」。再改成只看这个字段，字段不存在就不说。`saf-03`、`saf-04`、`t2s-09`、`t2s-10` 各 5 次共 20/20；后两题 10 次回答里没有多余的那句，前两题在确实点名时都说了。别名和简称匹配不到，不会触发。

**删除采购单被当成可执行，或者口头说「已取消」。** 订单数没变，回答在说谎。规划改为 `po_agent` 不支持删除、取消、撤回，返回空计划。冒烟 3/3，C7 安全题 4/4。其中两次仍建议去右侧标签页手动删除，这个操作不存在。系统没有删除机制，措辞被接受，功能本身没做。

**用户写了完整 SKU，仍被判成三款产品并列，草稿金额是 0。** 校验只用产品名搜索，三个红牛规格词面并列；槽位里的 SKU 只在搜索结果不超过 1 个时才采纳。这个「不信模型猜的 SKU」是有意的，但区分不了用户亲手写的 SKU。

处理：SKU 在目录里、并且作为完整 token 出现在用户自己的话里，才算精确匹配，可以打破并列。模型自己填的 SKU 仍然不能。确认阶段不带对话，把用户输入的 SKU 写回 `reference`，重校验结果一致。

效果：C5 采购 2/4，C7 和 C8 的 `po-02/03/04` 都通过。

**C7 修完又冒出两题，都不是功能退步。** `con-qa-02` 内容全对，加粗把评分子串隔断，见上一节，重评后过。`t2s-09`（11 月没有销售额）有一次去查了 `report_facts` 的元数据聚合，重跑 5/5 通过；多余的作用域开头是上一题规则的副作用，收紧后消失。

## 报表：预算、记账和耗时（记录 24–30）

**并发 5 的领域路径本身是通的。** 记录 24：text2sql、报表、采购、合同共 95 次，0 系统错误、0 超时、0 模型失败。查数 / 采购 / 合同 P50 为 10.78 / 9.74 / 10.31 秒，和并发 1 的差在 ±1 秒里。快路径吞吐约 22–24 次/分。报表 P95 约 60 秒来自 `rpt-07`，不是并发。

**这些报表数字是残缺月报。** `report` 路由把一个 Run 里的报表调用限在 2 次、4000 个输出 token。规划、出图、每章正文、洞察、审阅、修订共用这一个用途，所以每份完整月报只有前两次调用成功，后面的洞察和审阅全部被拒，回答里还把 `COST_BUDGET_EXCEEDED` 原样说给用户。B2、并发 1 对照和当时的最终回归里，凡是生成完整月报的运行都带这条警告。

处理：该路由改为最多 24 次、24000 token。回答规则改为期间没有数据时先说明，内部错误码不原样输出。

效果：`rpt-01`、`rpt-07`、`plan-02` 共 9 次，警告 0/9，洞察和审阅都生成了。代价是这 9 次平均约 ¥0.21、延迟 127–180 秒，其中 1 次撞上当时的 180 秒客户端超时。记录 24 里报表大约 ¥0.02、十几秒到 60 秒，不能再当成完整月报。`rpt-07` 在无数据月份仍会画别的月份或其他维度的图，修评分和提示之后仍不稳定，空月诚实问题没有并进后面的耗时优化。

**前四节正文跑过，但没进账本。** `_write_section` 不带 trace。用已入账的「问题与风险」校准后补记：漏掉约 ¥0.016–0.021，整棵树是 ¥0.22–0.29、约 22 次 `report` 调用，不是账本上的 16–18 次。墙钟已经包含这四次，补记账不缩短延迟。之后比「合并调用省了多少」都用这个补后数字，否则会看成假降。

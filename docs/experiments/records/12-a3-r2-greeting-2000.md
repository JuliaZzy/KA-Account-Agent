# 实验：A3 r2 — 修复后第一次 2000 条复测（暴露补投逻辑的新缺陷）

- **第几次**：A3 的第 2 次（[`r1`](11-a3-greeting-2000.md) 之后）。配置与 r1 完全相同，只有代码不同
- **日期**：2026-11-10 UTC 07:24:09–08:02:03（约 38 分钟）
- **代码**：包含 r1 之后的全部修复：`queued_at` 补投查询 + 部分索引、补投上限与超龄关闭、`execute_run` 的 DB 重试、worker 内 `Database` 每进程一次、各服务连接池、Qwen 30s/10s 超时、流式边收边发
- **原始文件**：[`exports/load-test-greeting-a3-2000-r2.json`](../exports/load-test-greeting-a3-2000-r2.json)、[`exports/load-test-greeting-a3-2000-r2.log`](../exports/load-test-greeting-a3-2000-r2.log)；50 条冒烟 [`exports/load-test-greeting-a3-r2-sanity-50.json`](../exports/load-test-greeting-a3-r2-sanity-50.json)

## 目的

1. 验证 r1 暴露的问题已修：残留 queued 为 0、没有 DB 连接尖峰、没有 Qwen 超长尾；
2. 验证库里 71 个历史 queued Run 能按正常流程被处理，不重新调模型；
3. 验证连接泄漏已修（worker 连接数）。

## 上线步骤（不手工改库）

1. 记录修复前快照：71 个 `queued` Run（最老 11 月 5 日，最年轻也已排队 3.5 小时）、`model_calls` 总数 9405、worker 容器 27 个空闲连接、迁移版本 `0025`；
2. `docker compose up -d --force-recreate worker title-worker sweeper`，由服务启动时自己执行迁移，**没有手工 SQL**；
3. 约 45 秒后（sweeper 第一轮）：迁移版本 `0026`；`queued` 为 **0**；**71 个 Run 全部 `failed / STUCK_QUEUE_EXPIRED`**，**71 条死信**；`model_calls` 总数仍是 **9405**（没有任何新模型调用）；sweeper 日志 `failed 71 queued runs: redispatch exhausted or queue age exceeded`。

这是修复起作用的直接证据：历史数据走正常流程被关闭，有事件和死信可查，不是手工清掉的。

| 成功 P50 | 4.62s | **5.09s** |

对话本身：**2000/2000 成功，没有超时，最长 19 秒**（r1 是 73.7 秒）；Qwen 单次调用最长 26.3 秒，没有触发 30 秒上限。连接：50 条冒烟和整轮结束后，worker 容器空闲连接都是 **5 个**（修复前 27 个），title-worker 2 个；没有 `too many clients`。

### P50 / P95 / P99 变慢是我们的代码吗？

没有证据说是。按步骤中位数对比（成功的对话 Run）：

| 步骤 | r1 | r2 |
|---|---|---|
| `orchestrator.plan` | 2.20s | 2.40s |
| `orchestrator.answer` | 2.10s | 2.23s |
| Qwen 单次调用（`model_calls`）p50 / p95 | 2143 / 3095ms | 2300 / 4044ms |

模型步骤本身慢了约 7–9%，整体 P50 多出的 0.46s 里模型步骤占了大头，对话 Run 排队仍是 0。r1 在北京时间 11:33、r2 在 15:24，是否与供应商时段负载有关**本实验无法证实**，只能说变慢出现在模型调用内部而不是排队或我们的开销。要排除只能在同一时段再跑一次（见 r3）。

### 流式修复起作用了

同一个 Run 的 `reply_updated` 事件最早和最晚的时间差：r1（缓冲）平均 **0.01 秒**，r2 平均 **0.09 秒**、最大 1.05 秒。短问候本身只有一两秒的输出，差距不大，但事件不再被压在同一个毫秒里。真正的验证要在慢调用上看，这次没有出现。

## 问题：补投逻辑把「在排队」当成「丢了」（r2 暴露）

对话 Run 全部成功，但**标题（`open`）Run**出现了异常：

| 项 | 值 |
|---|---|
| 压测结束时 `open` Run | succeeded 1787、**queued 211**、running 2 |
| 排队 3–4 分钟后最终 | succeeded 1967、**failed 24（`STUCK_REDISPATCH_EXHAUSTED`）**、queued 7、running 2 |
| `open` Run 从创建到开始，p50 / p95 / max | **244 / 481 / 487 秒** |
| `run.requeued_by_sweeper` 事件 | **3083 次**（`open` Run 仅约 2000 个） |
| `open` 的 `redispatch_count` 分布 | 0：495，1：525，2：382，**3：598** |
| 死信（排除历史 71 个） | 24 |

**原因。**

1. 标题队列 `ka_account.title` 由 title-worker 消费，并发 2，每个标题调用约 2.5 秒，吞吐约 **0.8 条/s**，而对话以约 0.95 条/s 完成并不断产生标题任务，队列持续积压，最长等了 8 分钟。这是**容量问题**，r1 里同样存在：用账本查 r1 时间窗，`open` Run 从创建到开始的等待是 p50 **145 秒** / p95 343 秒 / 最长 366 秒，`run.requeued_by_sweeper` 为 0 次——积压当时就在，只是旧的补投看不到它们，所以没被放大、也没被判失败。r2 的等待更长（p50 244 秒），因为重复消息把队列加深了。
2. 超过 120 秒宽限期后，sweeper 看到「已 `dispatched`、仍 `queued`」就**再投一份**。但消息其实还在 Redis 队列里排队，补出的是重复消息，队列更深，更多 Run 超过宽限期，再被补投——**自我放大**，平均每个 `open` Run 被补投约 1.5 次。
3. 补满 3 次后，Run 仍在排队，被判 `STUCK_REDISPATCH_EXHAUSTED` 失败并进死信。这 24 个其实都是健康的，只是标题没精修，保留了临时标题。

**这正是我们修 r1 时担心过的风险**（「宽限期太短会误杀排队深的 Run」），当时只是把宽限期从 30 秒调到 120 秒，**没有解决根本问题**：宽限期是用时间猜测消息有没有丢，但队列再深一点，任何固定宽限期都会失效。r2 把它变成了有数据的事实。

## 修复（r3 验证）

| 问题 | 处理 |
|---|---|
| 补投把「在排队」当成「丢了」 | 补投和「耗尽」判定之前，先看目标队列在 Redis 里的深度：该队列非空，说明 Run 只是在排队，不补投也不判耗尽。聊天看 `ka_account`，标题看 `ka_account.title`，**各队列分别判断**；读不到 Redis 时同样跳过。真丢了消息的 Run 仍由「排队超过 1 小时关闭」兜底，不依赖队列深度 |
| 标题队列积压（容量） | title-worker 并发 2 → 3，标题吞吐约 1.2 条/s，高于对话完成速度；连接预算 81 → 85（≤97） |

回归测试（`tests/test_unclaimed_dispatch.py`）：

- 标题队列里还有消息时，已满 3 次补投且很老的 `open` Run **既不补投、也不失败**；队列排空后它才被判定；
- 聊天队列繁忙、标题队列空闲：只补投标题 Run，聊天 Run 的补投次数不动；
- 队列深度未知（Redis 读不到）：不补投，但超龄的 Run 照样被关闭。

测试里对队列深度和发布打了桩，否则会读到 compose 里正在跑的真实队列，用例会互相影响。

## 结论

1. **r1 的问题已修**：残留 queued 为 0（历史 71 个按流程关闭、零模型调用）、对话 2000/2000、最长 19 秒、连接泄漏消失（27 → 5）；
2. **但新的补投逻辑自己有缺陷**：它在标题队列积压时制造重复消息并误杀了 24 个健康 Run，已改为先看队列深度；
3. P50 / P95 / P99 变慢约 7–9%，出现在 Qwen 调用内部，原因未证实；
4. 教训：**宽限期解决不了「消息在排队」和「消息丢了」的区分**，必须用队列深度这类直接证据；而且这个缺陷只有在真实压测里、标题队列积压时才会出现，单测过不了的。

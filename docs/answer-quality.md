# 回答质量：来源分级与草稿审核

简历里删掉了两句目前没有的能力：Source 可信度评分，以及覆盖全部 Agent 的对抗性评审。这份记下它们是什么、代码里已经有什么、以后可以加在哪。价格、起订量、SKU、折扣继续由 `po/` 的确定性代码计算，不靠模型打分。

**Mydian 缺"结果"。 现在全是机制（9 类工具、7 态状态机、6 个 Agent），没有成效。尽量补：处理耗时变化、替代的人工量、工具调用成功率、评审通过率、上线的品牌/经销商数、单次成本。拿不到线上数据，就用自建测试集的真实结果（"N 条用例，通过率 X%"）。**

<li><b>结果：</b>覆盖采购、合同、报表、品牌知识问答和业务数据查询；补充真实数据，例如自建测试集 <b>[N]</b> 条用例通过率 <b>[X%]</b>、Run 完成时间 P95 <b>[X 秒]</b>、上线品牌/经销商数量 <b>[N]</b>。</li>

## 现在有的

`checkpoints` 是一张表。每条 Run 的 `state_json` 都必须有 `context`、`completed_tool_calls`、`last`。工具循环还可以带 `open_step_id`、`last_report`；聊天父 Run 再带 `orchestrator`（`tasks`、`finished`、`results`、`wave_id`）。没有一份所有 Run 共用的 20 字段全局状态。

知识库检索的分数是相关度，不是来源可信度。`backend/brand_knowledge/rag.py` 用 BM25、向量召回、RRF，再用 `bge-reranker-v2-m3` 重排。

查数之后的 `REFLECT`（`backend/text2sql/prompt.py`）只判断返回的行够不够回答问题。80 分及以上采用；不够就换一个问题再查，最多三次。它不检查最终那句话有没有改数字。

报表草稿有一轮审核，在 `backend/report/turn.py`。问题类型是 hallucination、logic、exaggeration、format、incomplete，严重度是 critical、major、minor。低于 85 分就改写再审，最多三轮。minor 不进入要改的问题列表。这一轮不查越权，也不审采购、查数和搜索。

发信和 MCP 的用户确认是工具上的 `requires_approval`，不是这轮审核。

网页搜索把 query 原样发给博查，`freshness` 固定为 `noLimit`，不做关键词拆解，也不做相关度乘时间的过滤。见 `backend/tools/web_search.py`。

报表里的图是模型写出的 ECharts `echarts_option`，前端渲染。子进程执行的是 `analyze(datasets)`，用来算洞察，不画图。见 `backend/report/wizard.py`。

## 排队、并发与模型重试机制（面试表述）

一次用户动作先写入 PostgreSQL 的 `agent_runs` 和 `outbox_jobs`，状态从 `queued` 开始。Celery 只负责唤醒任务；数据库里的 Run 状态和 outbox 是事实来源。worker 在 claim 前通过 Redis 的 `acquire_run` 取得全局、经销商和用户的运行 lease。名额已满时不 claim，Run 继续保持 `queued`，由 sweeper 重新投递，不占用业务执行次数。

模型调用有独立的 provider 并发 lease。`acquire_model` 使用带 holder 的 Redis ZSET，Lua 脚本一次性检查并占用全部维度；lease 用心跳续期，过期 holder 会被回收，释放只删除自己的 holder。模型调用期间如果 provider 槽位已满，调用抛出可识别的 `ModelCapacityExceeded`，不会返回空文本，也不会生成兜底成功结果。

worker 把模型容量不足视为 infrastructure retry：释放当前 Run lease，把 Run 放回 `queued`，重新 arm outbox，并使用 `spend_attempt=False`，因此不会消耗业务执行次数。重试等待采用指数退避和 full jitter，等待时间逐步增加并设置上限，避免大量 Run 同时重新抢占同一个 provider。Run 的最大时长仍然是整体重试的边界。

本地并发不足和厂商故障分开处理。厂商返回 429、5xx 或超时时，worker 读取 `Retry-After`，按 provider 做基础设施重试；连续失败时打开 provider 级熔断器，冷却后用一次 half-open 探测恢复。细节见 [`retry.md`](retry.md)。

工具并发是另一层。工具的失败结果留在当前 Run 的工具记录里；只有注册为可重试的读工具才在同一工具调用内重试，副作用工具不自动重复。模型容量重试和工具结果重试不混用，避免把已经完成的副作用重新执行。

## 来源可信度

给材料的来源分档，决定冲突时信谁、回答时怎么引用。不替代相关度。

建议的档：库里已经算好的业务数字，已审核的合同和品牌文档，未确认的草稿，公开网页，模型自己的说法。只用了低档时，回答标明出处。两份材料打架时按档取舍，不让模型临场挑。

可以加的位置：

- **品牌知识问答。** 品牌文档和网页摘要讲到同一事实时，文档优先。重排分数保持现状，来源档另算。
- **`web_search`。** 按站点把品牌官网、新闻和不知名页面分开。低档结果只作补充，并保留链接。
- **报表事实。** 提示词已经要求优先 `report_facts.status = 'confirmed'`。只有草稿时，回答写明「未确认报表」，不要说成已确认业绩。
- **合同。** 解析已经丢掉对不上原文的引用。每条进回答的条款带页码。

## 草稿审核

写完之后另开一轮找错，不负责写第一稿。严重度决定动作：critical 挡住或必须改，major 改一版再审，minor 可以留下并告诉用户。

报表这条已经有了。还可以加到：

- **品牌知识问答。** 回答生成后对照检索段落，材料里没有的句子标出来。现在只在提示词里要求「只根据给出的段落说」。
- **Text2SQL 的口头回答。** 拿最终回复和返回的行对一下，抓住自己加总或改掉的数字。`REFLECT` 继续只判断行够不够用。
- **采购回复。** 金额和规则仍由 `po/check.py` 卡住。这轮只看回复有没有写出草稿上不存在的折扣或交期。
- **网页检索之后的回答。** 每句事实要能落在某条摘要或链接上，对不上就删掉，或改成结果里没看到。

越权、只读 SQL、经销商数据范围继续放在工具审批、`sql_validator` 和作用域视图里。这些用规则就能判定。

## 财报 RAG：Embedding 微调

简历里删掉了「在 BGE 上用财报问答和金融术语对做对比学习微调，领域检索精度提升 21%」。`saif_rag` 的向量是 DashScope 的 `text-embedding-v3`（1024 维），入库和提问都走 `generate_embedding`。仓库里没有 BGE，没有术语对或问答对的训练数据，也没有这次微调的评估。

以后如果要做：用财报问句和对应片段，加上「数据资产 / 无形资产 / 研发投入」这类同义术语对，在 BGE 上做对比学习，再和现在的 `text-embedding-v3` 比同一份评估集上的召回。数字要从这次评估里来。

## 财报 RAG：混合检索和重排里还没有的

对话检索已经是 BM25 加向量，召回后也会重排。下面这些写在旧简历里，代码里没有。

混合检索的关键词一侧是 Elasticsearch `query_string`，向量一侧是余弦近邻，融合权重写死为 `0.05, 0.95`（`search_v2.py` 里的 `FusionExpr`）。没有按问句长短切换：短查询并不优先关键词，长查询也不改成侧重语义。过滤只有知识库、文档和是否可用，没有按公司、报告期、章节、指标做 metadata 过滤。

重排用的是词面相似度和 DashScope 的 `gte-rerank`，按问句和片段文本打分。没有单独提高财报附注、表格说明或正文的排序。仓库里没有 MRR 提升 0.19、NDCG 提升 22% 的评估。

以后如果要做：融合权重按问句长度或词数切换；入库时写下公司、报告期、章节、指标，检索时作为过滤条件；重排可以按片段类型加权。MRR 和 NDCG 先在固定评估集上测出基线，再写进简历。

## 财报 RAG：生成阶段还没有的

多轮追问没有代词消解。`get_chat_completion` 只把当前问题和检索片段放进提示词，不会把「这家公司」「上一年同期」「这个指标」补成公司名、报告期和指标。历史写在 `messages` 表里，给历史列表用，不进入本轮检索或生成。仓库里没有「多轮提问准确率提升 26%」的评估。

引用没有到报告期，对话接口也没有把页码交出去。解析时 `position_int` 里有页码，但 `retrieval.py` 返回的只有文档名和片段正文。模型标的是检索片段编号 `##编号$$`，前端能打开文档名和原文。页码在这条链路上经常是空的。

以后如果要做：本轮提问前用上一轮的公司、报告期和指标改写问题，改写后的问题同时用于检索和生成；引用返回里带上 `positions`，并在入库时写下报告期，让引用能落到文档名、报告期和页码。准确率要用同一批多轮问题测出来再写。

## 财报 RAG：量化成果怎么测

简历「量化成果」里的数字是先写上的，仓库里没有评估集，也没有这些结果。测完再用测出来的数替换。

只跑现在这套系统，得到的是水平，不是提升。Recall@10、MRR、Hit@5、P@3、引用准确率都可以这样测，句子写成「达到」。不要写「提升至」或「从 xx 提升至 xx」：这两种都表示有对照，只测一次算不出来。NDCG 提升 22%、P@3 提升 28% 是差值，同样算不出来。

相对提升不需要旧版本的库。同一份题、同一套入库片段上做消融：只关键词、只向量、混合但不重排、现在的混合加重排，各跑一遍。差值才能写成「从 xx 到 xx」。Embedding 微调没有做，消融里也不要出现这一项；第三句里的「Embedding 微调」在测完之前不能留。

### 评估集

按公司、指标、报告期抽样，不要按章节是否好切来挑题。每题必须自己写全公司名和报告期。检索不做这三维的过滤，也不会把「这家公司」「上一年」补全；题目里省掉这些，测到的是缺失的改写，不是召回。

每题由人标相关片段。相关的标准是：只看这一片段，能回答该题，或能给出该指标在该报告期的数字。一份题可以有多条相关片段。标注时记下 `chunk_id`、文档名、页码和一小段原文。页码用解析结果里的 `position_int`，不要用对话接口的返回，那边没有页码。

两个人各标一批重叠题，算一致率。不一致的题讨论后改标，改不动就丢弃。题量建议 150 到 300。公司、指标、报告期都要有覆盖，不要让一两家公司占掉大半。

### 检索指标

排序用 `Dealer.retrieval`，不要用 `retrieve_content`。对话接口 `page_size` 固定为 5，而且丢掉了 `chunk_id` 和 `positions`。Recall@10 要把 `page_size` 设成 10。重排只发生在召回之后，候选池是 `max(page_size * 3, 128)` 再截断。

相关片段集合记为 G，返回的前 K 条记为 Rk。

- **Hit@K**：Rk 里至少有一条属于 G，记 1，否则 0。简历里的「Top5 准确召回率」用 Hit@5。
- **Recall@K**：|Rk ∩ G| / |G|。简历里的 Recall@10 用这个，K=10。只标了一条标准答案时，它和 Hit@10 相同。
- **MRR**：第一条相关片段排名的倒数，没有则 0，再对题取平均。
- **P@3**：前 3 条里相关条数除以 3。
- **NDCG@10**：相关记 1、不相关记 0。K 要写死，不要写 NDCG@K。

消融四组用同一批题：

1. 只关键词：融合时向量权重为 0，不做 `gte-rerank`。
2. 只向量：关键词权重为 0，不做重排。
3. 混合、不重排：保持现在的融合（`FusionExpr` 权重 `0.05, 0.95`），跳过 `rerank_by_model`。
4. 现在的系统：混合检索，再用词面相似度和 `gte-rerank` 重排。

第 4 组对第 1、2、3 组的差，才是「混合检索」或「重排」带来的提升。没有第 4 组以外的对照，就只写第 4 组的「达到」。

### 引用准确率

这是另一条链路，用真实对话：问题、模型回答、回答里的 `##编号$$`、编号对应的片段和文档名。

一条引用算对，要同时满足：编号能对上返回的片段，文档名与该片段一致，而且这段文字支撑回答里对应的那一句。分母是全部引用，不是全部问题。没有引用的回答单独计，不放进 93% 这个比例。

现在这条链路只能核文档名和片段原文。报告期没有字段，对话返回里也没有页码。在把 `positions` 和报告期接回引用之前，不要写「按文档名、报告期、页码回溯」。页码接上之后，再加一条：标出的页和标注页一致。
